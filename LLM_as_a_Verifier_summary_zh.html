文章摘要

本文提出了 LLM-as-a-Verifier —— 一个通用验证框架，旨在取代目前广泛使用的 LLM-as-a-Judge（以 LLM 作为评判者）范式，为智能体（agent）轨迹的质量评估提供更精细、更可靠的自动反馈信号。该工作的核心动机源于一个关键观察：标准的 LLM-as-a-Judge 方法要求模型输出单个离散评分 token（如 1 到 8 分），然后选取概率最高的 token 作为最终评分。这种粗粒度打分方式在面对复杂的智能体轨迹时常常无法区分优劣——两条质量不同的轨迹可能获得相同分数，从而导致大量"平局"。论文报告在 Terminal-Bench 上，标准 LLM-as-a-Judge 的平局率高达 27%。

为解决这一问题，作者将概念从"评判"（judge，形成整体意见并做出决策）上升为"验证"（verifier，确认真实性或正确性，需要更详细的评估），并从三个维度进行扩展：（1）评分粒度缩放——不直接取概率最高的 token，而是利用整个评分 token 的概率分布，将评分 token 集从 8 个扩展到最多 20 个，减少量化误差；（2）重复验证——对同一条轨迹进行多次独立验证（k = 1, 4, 16），通过集成降低单次评分的偏差和噪声；（3）标准分解——将整体轨迹质量拆分为三个互补维度分别评估：规范符合度（路径、命名等任务要求）、输出正确性（验证输出格式与预期结果是否匹配）、错误信号（轨迹是否无失败信号）。最终奖励值通过加权公式 R(t,τ) = (1/CK) · Σ_c Σ_k Σ_g p_θ(v_g | t, c, τ) · φ(v_g) 计算，即对多条标准、多次重复、多个评分粒度的概率求加权平均。

在 Terminal-Bench 2 和 SWE-Bench Verified 两个长周期基准上的实验表明：LLM-as-a-Verifier 的成对验证准确率达 78.9%，平局率为 0%（对比 Judge 的 26.5% 平局率）。当用作轨迹奖励模型进行测试时缩放（test-time scaling）时，该方法将 Terminal-Bench 的下游成功率从 81.8% 提升至 86.4%（SOTA），将 SWE-Bench Verified 提升至 77.8%（SOTA）。方法在多种智能体脚手架（ForgeCode、Terminus-Kira、Terminus 2）上表现出一致的提升效果，证明其具有插拔式的通用性。验证模型使用 Gemini 2.5 Flash，轨迹采样来自 Claude Opus 4.6、Gemini 3 Flash 和 Claude Opus 4.5 等前沿模型。

1. 提出问题

论文试图解决的核心问题是：如何为复杂智能体轨迹提供精细、可靠且无平局的自动质量评估？

作者首先诊断了当前 LLM-as-a-Judge 范式的根本缺陷。标准的做法是提示模型输出一个评分 token（如 1–8），然后选取概率最高的 token 作为最终离散评分。这一做法有两个关键问题：

第一，粗粒度评分导致的区分度不足。当比较两条复杂智能体轨迹时，标准方法常常给予相同评分——"standard LLM-as-a-Judge often assigns the same score (e.g., both trajectories receive a score of 4), resulting in a tie and failing to discriminate between them"。在 Terminal-Bench 上，这种粗粒度评分导致 27% 的平局。对于需要从多个候选轨迹中选出最优轨迹的下游任务而言，高平局率意味着评估信号几乎失效。

第二，单 token 离散化丢失了概率分布中的丰富信息。LLM 对每个评分 token 给出的概率分布本身就包含了不确定性、倾向性和细微差异的信号，但 argmax 操作将这些信息全部丢弃。作者在此提出了从"评判"到"验证"的范式转变：评判者形成一个整体意见并做出决策，而验证者确认真实性或正确性，需要更详细的评估——"a judge is one who forms an overall opinion and assigns a decision, whereas a verifier is one who confirms the truth or correctness of something and requires more detailed evaluations"。

此外，该问题在长周期、多步骤的智能体基准（如 Terminal-Bench 和 SWE-Bench）上尤为突出，因为这类任务中轨迹的差异往往是微小而关键的（如一个路径命名错误、一个中间步骤的失败信号），整体性的粗粒度评分根本无法捕捉这些差异。

2. 分析问题

作者将验证问题建模为一个成对轨迹比较的概率框架，并从中识别出可以通过三个可扩展维度来改进评分质量。

数学形式化。设 Vscore = {v1, …, vG} 为离散评分 token 的有序集合。给定任务提示 t、语言模型 pθ、评估标准 c 以及两条候选轨迹 τi 和 τj，作者构建评分提示并获得条件概率分布 pθ(v | t, c, τi) 和 pθ(v | t, c, τj)，通过提取 top logprobs 获得。与传统方法的关键区别在于：不将分布退化为单个离散评分，而是保留和使用整个概率分布。奖励的近似值为：

R(t,τ) = (1 / CK) · Σ_{c=1}^{C} Σ_{k=1}^{K} Σ_{g=1}^{G} p_θ(v_g | t,c,τ) · φ(v_g)

其中 C 为标准数量，K 为重复次数，G 为评分粒度级别，φ(vg) 将每个评分 token 映射为标量值。

三个可扩展维度。（1）评分粒度 G：从 8 个 token 扩展到最多 20 个（使用字母编码代替数字以启用 logprob 提取），更细的粒度减少了量化误差，使奖励能更精确地近似连续奖励曲面。（2）重复验证 K：单次验证可能存在偏差或噪声，通过多次独立验证取平均（集成策略），可以有效平滑这些随机误差。（3）标准分解 C = 3：将复杂的整体质量判断拆分为三个互补维度的二元验证任务——规范符合度（Specification：轨迹是否满足所有任务要求，如路径、命名等）、输出正确性（Output：验证输出格式是否匹配预期结果）、错误信号（Errors：轨迹是否无失败信号）。每个维度都比"这条轨迹总体上好不好"更简单、更明确。

成对锦标赛机制。为从 N 个候选中选出最优轨迹，采用轮询锦标赛（round-robin tournament）：对每对 (i, j) 分别计算 R(t, τi) 和 R(t, τj)，奖励高者获胜；在所有 C(N, 2) 对中获胜次数最多的轨迹即为最终输出。这一设计将 K 路选择问题转化为一系列二选一比较，既避免了直接排名的不稳定性，又从根本上消除了平局（因为奖励值是连续的实数，不再是离散的等级标签）。

3. 解决问题

论文的解决方案包含方法设计、实验验证和泛化性测试三个层面。

方法设计。LLM-as-a-Verifier 的提示模板将 LLM 定位为"专家评审者"角色：

"You are an expert [domain] reviewer. You will see a task description and two trajectories. Evaluation Criteria: [domain specific criteria]. Task: {task prompt} Trajectory A: {A} Trajectory B: {B}. Carefully analyze each trajectory, then provide your final scores: <score_A> INTEGER_1_TO_8 </score_A> <score_B> INTEGER_1_TO_8 </score_B>"

与传统 Judge 的关键区别在于：不使用 argmax 取最高概率 token，而是提取所有评分 token 的完整概率分布，按加权公式计算连续奖励值。实验中使用 Gemini 2.5 Flash 作为验证模型，轨迹由 Claude Opus 4.6、Gemini 3 Flash 和 Claude Opus 4.5 采样生成。

核心实验结果。

Verifier 在所有 k 值下均保持 7%-17% 的准确率优势。即使在 k=16 时重复验证已部分减轻 Judge 的平局问题（平局率降至 5.4%），Verifier 仍维持 7% 的准确率优势且平局率为 0%。

下游任务表现（测试时缩放）。在 Terminal-Bench 上使用 ForgeCode 作为智能体脚手架，采样 5 条轨迹，LLM-as-a-Verifier 将成功率从 81.8% 提升至 86.4%（SOTA）。在 SWE-Bench Verified 上，采样 3 条轨迹分别来自 Claude Opus 4.6、Gemini 3 Flash 和 Claude Opus 4.5，成功率达到 77.8%（SOTA）。

泛化性验证。LLM-as-a-Verifier 在三种不同智能体脚手架上均表现出一致提升：ForgeCode 达 86.4%，Terminus-Kira 达 79.4%，Terminus 2 达 71.2%。作者总结其方法是 "plug-and-play manner across any agent harness or model"。

缩放规律。实验表明验证准确率随着重复验证次数（1→16）和评分粒度（1→20）的增加持续提升。评分粒度的缩放通过减少量化误差使离散评分更好地近似底层连续奖励；重复验证的缩放通过集成平均消除单次评估的偏差和噪声；标准分解则通过让验证任务本身更简单、更明确来提升准确率。

4. 赞成什么

论文明确支持和继承以下思想与方法：

LLM 作为评估者的基本范式。论文并非否定 LLM-as-a-Judge，而是在其基础上进行改进和深化。LLM-as-a-Verifier 继承了使用 LLM 进行自动评估的可扩展性和可解释性优势（可扩展地替代人工评估、可提供详细反馈），但通过概率分布利用和细粒度评分解决了其核心缺陷。论文表态 "LLM-as-a-Verifier consistently outperforms LLM-as-a-Judge"，表明这是一种进化而非革命。

测试时计算缩放（test-time scaling）。论文的核心假设——通过增加测试时的计算量（更多次验证、更细粒度评分、更多标准）可以提升评估质量——与近年来 test-time compute scaling 的研究方向一脉相承。从 k=1 到 k=16，从 G=8 到 G=20，每一次缩放都带来了验证准确率的单调提升，验证了"更多推理计算→更好结果"的范式。

集成方法的有效性。重复验证（k=4, k=16）本质上是一种集成策略。论文的发现——"scores from individual verification can be biased or noisy, and an ensemble of repeated verifications helps average out these biases"——与机器学习中集成方法降低方差的经典理论相吻合。

分解复杂任务以提升准确性。将轨迹整体评估分解为规范符合度、输出正确性和错误信号三个子维度，体现了"分而治之"的设计哲学。这与思维链（Chain-of-Thought）将复杂推理分解为中间步骤、以及结构化评估中将评估标准分解为多维评分量规的做法思路一致。

开源与社区协作。论文将代码和数据全部开源在 GitHub 上（llm-as-a-verifier.github.io），并提供复现结果，继承了近年来 LLM 研究社区重视可复现性和开放协作的传统。

5. 反对什么

由于该作品为技术博客而非正式学术论文，明确的反对立场不多（缺少 Related Work 章节和与具体基线方法的详细对比）。以下部分为基于原文立场的归纳，部分为推断。

反对将 argmax 离散评分作为充分的评估信号。这是论文最核心的反对立场：当 LLM 输出评分 token 的概率分布时，仅取概率最高的 token 丢弃了分布中的绝大部分信息——"rather than reducing each distribution into a single discrete score, we approximate the reward of trajectories"。论文通过实验表明，保留和使用完整概率分布可以将验证准确率从 57.0% 提升至 74.7%（k=1 下）。

反对在评估中接受高平局率。在 Terminal-Bench 上 27% 的平局率意味着评估系统面对近三分之一的比较时完全无法提供有用信号。论文的设计目标之一是将平局率降至零，并通过连续奖励值的锦标赛机制实现了这一目标。这实质上否定了"平局是一个可以接受的评估输出"的假设。

反对将整体性评分等同于细致验证。论文通过概念区分——judge 形成整体意见，verifier 确认正确性——反对了"一个好的评判者只需要输出一个总分"的简化观点。标准分解（C=3）的实验结果表明，将验证拆分为更简单、更明确的子任务可以提升准确性——"decomposing trajectory verification into complementary factors improves accuracy"。

（推断）潜在局限性。博客未明确讨论该方法的局限性，但可推断：将 K 和 C 扩展会线性增加 API 调用成本（k=16 且 C=3 意味着每对比较需要 16×3=48 次独立 LLM 调用）；方法在 Terminal-Bench 和 SWE-Bench 两个代码/命令领域外的泛化性尚未验证；使用 Gemini 2.5 Flash 作为验证模型，切换到其他模型的效果未报道。
